# ADR-0002: Radicale as the CalDAV hub

- Status: Accepted (retroactive — documents a decision already implemented)
- Date: 2026-08-26

## Context

The canonical collections produced by `merge-ucrawler.py` need to be reachable
by ordinary calendar and task clients (Thunderbird and the like) on the local
network, not only by the sync pipeline. Deadlines are VTODO and delivery windows
are VEVENT, so the server has to accept both component types in the collections
it hosts, and the store has to be writable by clients so that user task state
(`STATUS`, `COMPLETED`, `PERCENT-COMPLETE`) can flow back into the pipeline —
that flow-back is what ADR-0004 depends on.

## Decision

Radicale (`ghcr.io/kozea/radicale:stable`) runs as a service in the same Compose
project and is the CalDAV hub. Its configuration is bind-mounted read-only; its
collection store is a persistent bind mount.

Authentication is `htpasswd` against `/etc/radicale/users` with
`htpasswd_encryption = autodetect`, and authorization is `owner_only`: a user can
reach only the collections under their own principal. There is one account, whose
credentials come from `RADICALE_USER` / `RADICALE_PASSWORD` in `.env` and are
passed into the `caldir` container.

`provision-radicale.sh` creates one collection per course × kind. For every
`202615_*` directory that has a `deadlines` or `windows` subdirectory it issues an
`MKCOL` against `<RADICALE_URL>/<RADICALE_USER>/<course>__<kind>/` declaring a
supported component set of `VEVENT` **and** `VTODO`, plus a displayname equal to
the flat collection name. HTTP 200, 201, 204 and 405 are all accepted (405 being
"already there"); anything else fails the run.

`caldir` reaches Radicale through its CalDAV provider. Provisioning writes the
collection's `.caldir/config.toml` with `provider = "caldav"`,
`caldav_account = "<user>@radicale"`, the collection URL, and
`caldav_supports_tasks = true`. Configs written before that capability key existed
are migrated in place by appending the key rather than being rewritten.

## Consequences

- One CalDAV endpoint serves every course collection, and any standard client can
  subscribe without knowing anything about the pipeline.
- Because each collection is declared with both `VEVENT` and `VTODO`, the same
  server hosts the deadline task lists and the window calendars without a
  per-kind server configuration.
- `caldav_supports_tasks = true` is what lets `caldir sync` push VTODO to
  Radicale; a collection whose config predates the key would silently not carry
  tasks, which is why the migration branch exists and runs on every provisioning
  pass.
- The provisioning step is idempotent and safe to run on every sync: the MKCOL is
  attempted only when the local config file is absent, and 405 from an existing
  collection is not an error.
- `owner_only` plus a single account means the access model is all-or-nothing.
  Sharing one collection with someone means sharing the account.
- The `users` file is not generated by anything in the repository: it is created
  by hand with `htpasswd` and is gitignored, so a fresh deployment has an extra
  manual step before the pipeline can authenticate (see ADR-0007).
- Radicale listens on all interfaces inside the container, and the published port
  is bound to one specific host address in `compose.yaml`, which ties the Compose
  file to a particular host's network layout.
